# Single-slice (D) run on Euler: SLURM translation, gaps, and space budget

Scope: slice D only, through somatic calling with GATK4 Mutect2 (originally MuTect1; see
"Correction: MuTect1 -> Mutect2" below), producing per-cluster somatic VCFs. Slices A, B,
C, E are untouched. Scripts live in `realdata/scripts/euler/` (`config.sh` plus
`00_download.sbatch` through `07_copy_out.sbatch`, `submit_all.sh`,
`build_cluster_bams.py`). Nothing has been submitted -- `sbatch` has not been run.

## What changed going from the LSF originals to SLURM

Stage-by-stage, `preprocessing/{1,2,3}_*.sh` -> `01_preprocess.sbatch`, `split.sh`'s
`split_bams` -> `02_split_chrom.sbatch` (one SLURM array task per cell instead of one
`bsub` per 100 files), `clustering.sh`'s `create_pileup` -> `03_pileup.sbatch` (one array
task per chromosome, same per-chromosome scratch-copy-then-cleanup pattern as the
original), `clustering.sh`'s `variant_calling` -> `04_secedo.sbatch`, `mutect.sh` ->
`06_mutect.sbatch` (one array task per cluster x chromosome, task list generated by
stage 05; runs GATK4 Mutect2 + FilterMutectCalls, not MuTect1 -- see "Correction:
MuTect1 -> Mutect2" below). `00_download.sbatch` and `07_copy_out.sbatch` are new (the
originals assumed data already sitting on `/cluster/work/grlab/...` and never had a
copy-out step).

## Gaps found while translating (beyond the four in `breast_cancer_plan.md`)

These came from reading `mutect.sh` and secedo's `secedo_main.cpp`/`pileup_main.cpp`
directly, not from the earlier read-through -- recorded here rather than glossed over.

1. **`--merge_file` is a coverage-pooling trick, not needed for a single real slice.**
   Its own flag help in `secedo_main.cpp` says it "only works on synthetic data where we
   know consecutive cells are part of the same cluster" -- it merges adjacent cells to
   artificially inflate coverage for testing. There is no `breast_group_D_*` file in
   `secedo-evaluation` (only `ABCDE`/`B`-specific ones, built for their multi-slice
   pooling runs) because none is needed: omitting `--merge_file` for slice D makes
   `secedo` use the identity grouping, which is the correct behaviour for real,
   unmerged single cells, not a workaround.
2. **`mutect.sh` assumes per-cluster whole-genome BAMs that no script builds.** It reads
   `clone<n>_1Y.bam` directly. `secedo` only ever writes a flat `clustering` file
   (cell-index -> cluster-id) plus, from `pileup`, a `<prefix>_<chromosome>.map` file
   (cell-index -> original per-cell BAM name). `build_cluster_bams.py` (ours, stage 05)
   joins the two and `samtools merge`s each cluster's per-cell BAMs into
   `clone<cluster_id>.bam`.
3. **The pseudo-normal cluster ID is data-dependent.** The original hardcodes
   `clone19` for slice B; which cluster stands in as the matched normal for slice D
   can't be known until stage 04/05 produce slice D's actual clustering. `06_mutect`
   refuses to run until `NORMAL_CLUSTER_ID` is set in `config.sh` after inspecting
   stage 05's output, rather than guessing.
4. **(Superseded by the Mutect2 switch.)** The original gap here was that `mutect.sh`
   only asked MuTect1 for the call-stats `.txt`, not a VCF, so the SLURM translation had
   to add `--vcf <path>` itself. Moot now: Mutect2 always writes a VCF (`-O <path>`),
   and `06_mutect.sbatch` additionally runs FilterMutectCalls and a PASS/SNP-only select
   on it -- see "Correction: MuTect1 -> Mutect2" below for the full account.
5. **The `PER_CELL_SUMMARY_FILE` gap from the earlier plan is resolved, not open.**
   10x hosts slice D's own `breast_tissue_D_2k_per_cell_summary_metrics.csv` at the
   same download host as the BAM (confirmed via HTTP HEAD, 425 KB) -- `00_download`
   fetches it, so the allowed-barcode list for stage 3's CB split is the genuine
   Cell Ranger output, not a reconstruction.

## Correction: MuTect1 -> Mutect2 (Jack approved, 2026-09-08)

The "Dependency check" below originally concluded the SECEDO-faithful MuTect1 path was
viable on Euler and there was no need to substitute GATK4 Mutect2. That verdict is
overturned, not by anything wrong with the Zulu-JDK-7 fix itself (it worked), but because
the MuTect 1.1.4 jar is a separate, harder prerequisite: it needs a personal Broad
download of a now-discontinued, unversioned artefact, with no current official mirror.
Jack approved switching to GATK4 Mutect2 instead, so `06_mutect.sbatch` now runs Mutect2
in place of MuTect1, and the Zulu-JDK-7 fetch and `MUTECT_JAVA`/`MUTECT_JAR` config
entries are removed (Mutect2 runs on modern Java -- Euler's own `openjdk` module stack
covers it, no special JDK needed any more).

What carries over unchanged: the germline design. Tumour cluster called against the
chosen pseudo-normal cluster, exactly as before -- one SECEDO cluster stands in as the
matched normal, `NORMAL_CLUSTER_ID` selection at stage 05 is untouched, and Mutect2 runs
in tumour-normal mode (`-I tumour -I normal -normal <normal_sample>`), not tumour-only
mode. Tumour-only mode would drop this germline subtraction and change the somatic
calls -- deliberately avoided.

What's new because Mutect2 needs it and MuTect1 didn't:

- **FilterMutectCalls.** MuTect1 emitted a finished call set directly (LOD thresholds
  baked into the one pass); Mutect2's raw output is unfiltered candidate calls with
  FILTER annotations, so `06_mutect.sbatch` now runs FilterMutectCalls and keeps only
  PASS variants. No gnomAD germline-resource or Panel of Normals is wired in yet -- the
  pseudo-normal alone is the germline subtraction for this feasibility run. Both are
  optional refinements: a `--germline-resource` (gnomAD, population allele frequencies)
  would sharpen contamination/germline filtering, and a proper Panel of Normals (ideally
  CHISEL-identified normal cells, per `breast_cancer_plan.md`'s stage 7 note, rather than
  ad hoc) would catch recurrent artefacts a single pseudo-normal cluster can't. Neither
  is needed to get a first read on slice D's somatic spectra.
- **Per-cluster read-group retagging.** `build_cluster_bams.py` (stage 05) merges
  per-cell BAMs that all carry the *same* original 10x `@RG SM` tag (splitting/merging by
  cell barcode never touches read groups). MuTect1's `--input_file:tumor`/`:normal` tags
  didn't care which sample name was on which file; GATK4 Mutect2's `-normal <sample>`
  decides tumour vs normal by matching read-group SM across *all* `-I` inputs together, so
  two same-SM BAMs would put every read -- tumour's included -- in the "normal" role.
  `06_mutect.sbatch` retags each cluster's merged BAM with a unique synthetic SM
  (`samtools addreplacerg`) before calling Mutect2, flock-guarded so the chromosome tasks
  sharing a cluster don't race to do it.
- **SNP-only restriction, with MNP merging disabled.** Mutect2 is assembly-based and
  calls indels too, which MuTect1's pileup-based test never could. The 96-channel SBS
  binning this pipeline feeds has no use for indels, so `06_mutect.sbatch` selects
  PASS + SNP-type only, keeping stage 07's somatic-count summary meaning what it meant
  before (somatic SNVs). Mutect2's assembly can also phase adjacent substitutions into a
  single MNP record by default, which a plain SNP-only filter would drop wholesale rather
  than decompose -- losing both underlying SBS events at that site, not just one, and
  corrupting the 96-channel spectra by that much. Rather than accept that loss,
  `06_mutect.sbatch` passes `--max-mnp-distance 0` to Mutect2, which turns off the MNP
  merging so adjacent phased substitutions stay as separate SNP records; the SNP-only
  select then only ever removes indels.
- **Mutect2 heap pinned with `-Xmx6g`.** Left to its default, the GATK JVM sizes its heap
  from the node's total physical RAM rather than the SLURM cgroup's actual allocation, so
  an unpinned Mutect2/FilterMutectCalls/SelectVariants call can size a heap larger than
  the job's `--mem-per-cpu=4G x --cpus-per-task=2 = 8G` budget and get killed for
  exceeding its cgroup limit. `06_mutect.sbatch` passes `--java-options "-Xmx6g"` to every
  `gatk` invocation to keep the heap safely under that 8G ceiling.

What's now unused: **COSMIC_VCF and DBSNP_VCF are no longer consumed by this stage.**
MuTect1's `--dbsnp`/`--cosmic` fed its own LOD-threshold classifier (stricter at dbSNP
sites, relaxed at COSMIC hotspots) -- a mechanism GATK4 replaced with germline-resource
population-AF filtering and Panels of Normals. Neither COSMIC (a mutation catalogue, not
population frequencies) nor this dbSNP file can serve as a `--germline-resource` as-is
(that needs an AF INFO field). Both stay defined in `config.sh` and staged by
`00_download` (harmless, and dbSNP or an AF-annotated resource may still be useful for a
future `--germline-resource` refinement), but neither blocks stage 06 any more and
neither is referenced by it.

## SECEDO build flags on modern GCC

Undocumented until now: building `secedo` (stage 06's upstream dependency, not part of
this Mutect2 change) against Euler's current GCC needs two warnings-as-errors suppressed
that the original code didn't anticipate -- `-Wno-error=stringop-overflow` and
`-Wno-error=restrict`. Pass both to the CMake build (e.g.
`-DCMAKE_CXX_FLAGS="-Wno-error=stringop-overflow -Wno-error=restrict"`) or add them to
the compiler invocation directly; without them the build fails outright on a modern GCC
that promotes these checks to errors under `-Werror`, rather than the warnings they were
when the code was written.

## Dependency check: MuTect1 + Java on Euler, and the COSMIC build

Checked before launching anything, since both would have blocked the run behind the
170 GB slice-D transfer if found late. Superseded by the Mutect2 switch above for the
Java/MuTect1-jar conclusion; kept here as the record of what was actually checked.

- **Euler has no Java 6/7/8 module.** Its current module stack (and the GDC group's)
  lists only `openjdk/11.0.23_9`, `openjdk/17.0.11_9`, `openjdk/21.0.3_9`. Not the
  actual blocker, though: MuTect1 is a plain `java -jar`, never a module -- the original
  `mutect.sh` already assumed a personal JRE, not an installed one.
- **MuTect1 needs Java 7, not Java 6** as the original script's own `~/jre1.6.0_45`
  path implied. GATK/MuTect-era code (Queue, cofoja-based contracts) relies on
  `sun.reflect`/`sun.misc` internals that Java 9+'s module system hides -- a removed-API
  break, not a class-file-version mismatch a newer JVM would simply tolerate.
- **Java itself was resolved without a module or an account** (Oracle's own JRE/JDK
  archive now gates old versions behind a login; Azul's Zulu builds of OpenJDK don't, and
  cover Java 7 -- downloaded and ran `zulu7.56.0.11-ca-jdk7.0.352-linux_x64.tar.gz` to
  confirm: reports `openjdk version "1.7.0_352"` and launches cleanly), but the MuTect
  1.1.4 jar itself was not -- it needs a personal Broad download with no current official
  mirror, discontinued and hard to obtain, which is what actually forced the Mutect2
  switch above (Java was never the blocker in the end).
- **COSMIC build confirmed GRCh37.** `COSMIC_sig/cosmic_signatures.csv` carried no
  build metadata in the commit that added it, so this was checked numerically:
  diffed against COSMIC's own current release (v3.4 SBS, both GRCh37 and GRCh38,
  fetched directly, no login needed). All 8 of our 10 signatures present in v3.4
  (SBS1, SBS4, SBS5, SBS36, SBS37, SBS40a, SBS44, SBS92) match GRCh37 to
  floating-point precision and are clearly distinct from GRCh38 (differs from the 3rd
  significant digit on, even on the first channel checked). SBS105 and SBS112 aren't in
  v3.4 (presumably added in a later COSMIC release) so weren't cross-checked directly,
  but nothing suggests they're a different build than the rest of the same file. This
  check is orthogonal to the Mutect2 switch (COSMIC's build, not its use) and still
  stands, even though COSMIC is no longer consumed by stage 06 itself.

## Peak scratch usage for slice D

Two figures: a realistic one (the scripts as written, with the one cheap cleanup they
do -- dropping the pre-sort CB-filtered BAM once its sorted copy exists), and a
deliberately pessimistic ceiling assuming *no* intermediate is ever deleted and every
stage's output coexists with every other stage's, to check the realistic figure isn't
hiding a fragile margin.

| Item | Size | Basis |
|---|---:|---|
| Reference (decompressed FASTA + `.fai`) | 3 GB | measured (870 MB gzipped, ~3.4x expansion) |
| Raw BAM + BAI + summary CSV | 169.5 GB | measured (HTTP HEAD) |
| Stage 1 filtered BAM | <=170 GB | filtering only removes reads, upper-bounded by input |
| Stage 2 CB-filtered BAM (sorted) | <=170 GB | same bound |
| Per-cell BAMs (`cell_bams/`) | <=170 GB | repartition of the same reads, not a size increase |
| Per-chromosome split (`cell_bams_split/`) | <=170 GB | repartition of the same reads again |
| Pileup transient copies (per-chromosome, concurrent worst case) | <=170 GB | sum across chromosomes repartitions the same read volume once more |
| Pileup outputs (23 chromosomes) | ~15 GB | SECEDO's README: ~35 GB pileup output at 8000 cells/0.5x; slice D is ~2000 cells, scaled and rounded up |
| SECEDO clustering + reference-relative VCFs | <1 GB | flat text/small binary outputs |
| Cluster-merged BAMs (`cluster_bams/`), plus retagged copies Mutect2 needs | <=340 GB | regrouping of the per-cell BAMs (ours, stage 05), roughly doubled by the retagged `clone*.tagged.bam` copies stage 06 now makes alongside them |
| Mutect2 outputs (raw + filtered + final PASS/SNP VCFs, all clusters x chromosomes) | ~10 GB | small per-file VCF/stats, tens of clusters x 24 chromosomes -- no call-stats/coverage side files any more, but three VCF stages per task instead of MuTect1's one |
| dbSNP (decompressed) | ~10 GB | 1.55 GB gzipped (measured), expanded and rounded up -- staged but no longer used by stage 06 (see "Correction" above) |
| COSMIC (decompressed, placeholder) | ~10 GB | not yet in hand -- placeholder upper bound if staged for a future refinement; no longer needed to run stage 06 |

**Pessimistic sum (nothing ever deleted, every stage's output alive at once): ~1.41 TB**
(up from ~1.24 TB before the Mutect2 switch -- the retagged BAM copies stage 06 now
makes account for the difference) -- still comfortably clear of the 2.5 TB scratch
quota. **Realistic running peak** (the scripts' actual cleanup: the raw BAM,
filtered BAM, per-cell BAMs, and per-chromosome split are all kept -- there's no need
to delete anything to stay in budget -- only the redundant pre-sort CB-filtered copy is
dropped) is lower still, on the same order as the pessimistic figure minus that one
duplicate, i.e. still comfortably under 2.5 TB. Slice D fits with substantial headroom
either way; no aggressive intermediate cleanup is required for space reasons (the
scripts still do the one cheap deletion as hygiene, not because it's needed to fit).

## Must-have: copy-out on completion

`07_copy_out.sbatch` copies the per-cluster somatic VCFs (final PASS/SNP-only, from
FilterMutectCalls + SelectVariants -- no call-stats/coverage side files any more, MuTect1
had those, Mutect2 doesn't produce an equivalent), the SECEDO clustering assignment and
reference-relative VCFs, and this run's logs to `PERSIST_DIR`, then verifies the VCF
count matches before declaring success.
`submit_all.sh` chains it with `--dependency=afterany` (not `afterok`) on the mutect
array job, so the copy still runs -- and reports what did or didn't complete -- even if
some (cluster, chromosome) tasks fail, rather than stranding a completed subset in
scratch.

## Report at completion

Once the run finishes, report explicitly: **how many clusters SECEDO found** (stage 05's
`n_clusters` line) and **the somatic SNV count per cluster**, summed across chromosomes
(stage 07's `cluster_summary.csv`). This is the number that tells us whether slice D's
real-data regime lands in the sparse tens-to-hundreds-of-mutations-per-node range
Tree-HDP is built for, or somewhere else -- the actual point of running this slice.
