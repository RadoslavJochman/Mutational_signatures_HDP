# Single-slice (D) run on Euler: SLURM translation, gaps, and space budget

Scope: slice D only, through MuTect1 somatic calling, producing per-cluster somatic
VCFs. Slices A, B, C, E are untouched. Scripts live in `realdata/scripts/euler/`
(`config.sh` plus `00_download.sbatch` through `07_copy_out.sbatch`, `submit_all.sh`,
`build_cluster_bams.py`). Nothing has been submitted -- `sbatch` has not been run.

## What changed going from the LSF originals to SLURM

Stage-by-stage, `preprocessing/{1,2,3}_*.sh` -> `01_preprocess.sbatch`, `split.sh`'s
`split_bams` -> `02_split_chrom.sbatch` (one SLURM array task per cell instead of one
`bsub` per 100 files), `clustering.sh`'s `create_pileup` -> `03_pileup.sbatch` (one array
task per chromosome, same per-chromosome scratch-copy-then-cleanup pattern as the
original), `clustering.sh`'s `variant_calling` -> `04_secedo.sbatch`, `mutect.sh` ->
`06_mutect.sbatch` (one array task per cluster x chromosome, task list generated by
stage 05). `00_download.sbatch` and `07_copy_out.sbatch` are new (the originals assumed
data already sitting on `/cluster/work/grlab/...` and never had a copy-out step).

## Gaps found while translating (beyond the four in `breast_cancer_plan.md`)

These came from reading `mutect.sh` and secedo's `secedo_main.cpp`/`pileup_main.cpp`
directly, not from the earlier read-through -- recorded here rather than glossed over.

1. **`--merge_file` is a coverage-pooling trick, not needed for a single real slice.**
   Its own flag help in `secedo_main.cpp` says it "only works on synthetic data where we
   know consecutive cells are part of the same cluster" -- it merges adjacent cells to
   artificially inflate coverage for testing. There is no `breast_group_D_*` file in
   `secedo-evaluation` (only `ABCDE`/`B`-specific ones, built for their multi-slice
   pooling runs) because none is needed: omitting `--merge_file` for slice D makes
   `secedo` use the identity grouping, which is the correct behaviour for real,
   unmerged single cells, not a workaround.
2. **`mutect.sh` assumes per-cluster whole-genome BAMs that no script builds.** It reads
   `clone<n>_1Y.bam` directly. `secedo` only ever writes a flat `clustering` file
   (cell-index -> cluster-id) plus, from `pileup`, a `<prefix>_<chromosome>.map` file
   (cell-index -> original per-cell BAM name). `build_cluster_bams.py` (ours, stage 05)
   joins the two and `samtools merge`s each cluster's per-cell BAMs into
   `clone<cluster_id>.bam`.
3. **The pseudo-normal cluster ID is data-dependent.** The original hardcodes
   `clone19` for slice B; which cluster stands in as the matched normal for slice D
   can't be known until stage 04/05 produce slice D's actual clustering. `06_mutect`
   refuses to run until `NORMAL_CLUSTER_ID` is set in `config.sh` after inspecting
   stage 05's output, rather than guessing.
4. **`mutect.sh` only asks MuTect1 for the call-stats `.txt`, not a VCF.** Per-cluster
   somatic VCFs are the actual target here, so `06_mutect.sbatch` adds `--vcf <path>` to
   the same MuTect1 call (same inputs, same normal/tumour logic) rather than
   post-processing the call-stats file ourselves.
5. **The `PER_CELL_SUMMARY_FILE` gap from the earlier plan is resolved, not open.**
   10x hosts slice D's own `breast_tissue_D_2k_per_cell_summary_metrics.csv` at the
   same download host as the BAM (confirmed via HTTP HEAD, 425 KB) -- `00_download`
   fetches it, so the allowed-barcode list for stage 3's CB split is the genuine
   Cell Ranger output, not a reconstruction.

## Prerequisites you supply (not fetchable by either repo, unattended)

- **COSMIC VCF**: needs your own registered COSMIC account; `00_download` and
  `06_mutect` both refuse to proceed silently without it at `COSMIC_VCF`. Expected
  filename/path (override by exporting `COSMIC_VCF` before submitting):
  `${SCRATCH}/secedo_slice_d/ref/cosmic_v94_hg37_coding_and_noncoding.vcf` (or your
  closest available GRCh37 COSMIC release, renamed to that or pointed at via
  `COSMIC_VCF`) -- alongside the reference and dbSNP in the same scratch `ref/`
  directory. Must be GRCh37: confirmed separately (see "Dependency check" below) that
  the repo's own `COSMIC_sig/cosmic_signatures.csv` already is, so this is the only
  remaining build check. Note scratch is purged/unbacked-up, so this file doesn't
  survive an idle gap between staging it and running the pipeline -- stage it close to
  submission, not far ahead of it.
- **MuTect 1.1.4 jar**: needs your own copy (Broad login); the original script already
  assumed a personal `~/mutect/muTect-1.1.4.jar`, not something either repo installs.
  Expected path: `${HOME}/mutect/muTect-1.1.4.jar` (override via `MUTECT_JAR`).
- **`PERSIST_DIR`**: defaults to `$HOME/secedo_runs/slice_D` in `config.sh`. Confirm
  that's where you want the final VCFs, or point it at your group's `/cluster/work`
  storage instead if you'd rather keep it off `$HOME`'s quota.
- dbSNP and the Java 7 runtime are *not* on this list any more (see below) -- both are
  fetched automatically by `00_download`, needing no account.

## Dependency check: MuTect1 + Java on Euler, and the COSMIC build

Checked before launching anything, since both would have blocked the run behind the
170 GB slice-D transfer if found late.

- **Euler has no Java 6/7/8 module.** Its current module stack (and the GDC group's)
  lists only `openjdk/11.0.23_9`, `openjdk/17.0.11_9`, `openjdk/21.0.3_9`. Not the
  actual blocker, though: MuTect1 is a plain `java -jar`, never a module -- the original
  `mutect.sh` already assumed a personal JRE, not an installed one.
- **MuTect1 needs Java 7, not Java 6** as the original script's own `~/jre1.6.0_45`
  path implied. GATK/MuTect-era code (Queue, cofoja-based contracts) relies on
  `sun.reflect`/`sun.misc` internals that Java 9+'s module system hides -- a removed-API
  break, not a class-file-version mismatch a newer JVM would simply tolerate.
- **Resolved without a module or an account.** Oracle's own JRE/JDK archive now gates
  old versions behind a login; Azul's Zulu builds of OpenJDK don't, and cover Java 7.
  Downloaded and ran `zulu7.56.0.11-ca-jdk7.0.352-linux_x64.tar.gz` to confirm: reports
  `openjdk version "1.7.0_352"` and launches cleanly. `00_download.sbatch` now fetches
  and unpacks this into `$HOME/secedo_tools/zulu7` (small, reusable, kept outside
  scratch so it survives a purge), and `config.sh` points `MUTECT_JAVA` there by
  default. Verdict: the SECEDO-faithful MuTect1 path is viable on Euler; no need to
  substitute GATK4 Mutect2.
- **COSMIC build confirmed GRCh37.** `COSMIC_sig/cosmic_signatures.csv` carried no
  build metadata in the commit that added it, so this was checked numerically:
  diffed against COSMIC's own current release (v3.4 SBS, both GRCh37 and GRCh38,
  fetched directly, no login needed). All 8 of our 10 signatures present in v3.4
  (SBS1, SBS4, SBS5, SBS36, SBS37, SBS40a, SBS44, SBS92) match GRCh37 to
  floating-point precision and are clearly distinct from GRCh38 (differs from the 3rd
  significant digit on, even on the first channel checked). SBS105 and SBS112 aren't in
  v3.4 (presumably added in a later COSMIC release) so weren't cross-checked directly,
  but nothing suggests they're a different build than the rest of the same file. No
  fix needed -- matches the reference used throughout this pipeline.

## Peak scratch usage for slice D

Two figures: a realistic one (the scripts as written, with the one cheap cleanup they
do -- dropping the pre-sort CB-filtered BAM once its sorted copy exists), and a
deliberately pessimistic ceiling assuming *no* intermediate is ever deleted and every
stage's output coexists with every other stage's, to check the realistic figure isn't
hiding a fragile margin.

| Item | Size | Basis |
|---|---:|---|
| Reference (decompressed FASTA + `.fai`) | 3 GB | measured (870 MB gzipped, ~3.4x expansion) |
| Raw BAM + BAI + summary CSV | 169.5 GB | measured (HTTP HEAD) |
| Stage 1 filtered BAM | <=170 GB | filtering only removes reads, upper-bounded by input |
| Stage 2 CB-filtered BAM (sorted) | <=170 GB | same bound |
| Per-cell BAMs (`cell_bams/`) | <=170 GB | repartition of the same reads, not a size increase |
| Per-chromosome split (`cell_bams_split/`) | <=170 GB | repartition of the same reads again |
| Pileup transient copies (per-chromosome, concurrent worst case) | <=170 GB | sum across chromosomes repartitions the same read volume once more |
| Pileup outputs (23 chromosomes) | ~15 GB | SECEDO's README: ~35 GB pileup output at 8000 cells/0.5x; slice D is ~2000 cells, scaled and rounded up |
| SECEDO clustering + reference-relative VCFs | <1 GB | flat text/small binary outputs |
| Cluster-merged BAMs (`cluster_bams/`) | <=170 GB | regrouping of the per-cell BAMs, ours (stage 05) |
| MuTect1 outputs (call-stats + coverage + VCF, all clusters x chromosomes) | ~10 GB | small per-file text/VCF, tens of clusters x 24 chromosomes |
| dbSNP (decompressed) | ~10 GB | 1.55 GB gzipped (measured), expanded and rounded up |
| COSMIC (decompressed, placeholder) | ~10 GB | not yet in hand -- placeholder upper bound, confirm once staged |

**Pessimistic sum (nothing ever deleted, every stage's output alive at once): ~1.24 TB**
-- roughly half of the 2.5 TB scratch quota, comfortably clear even under this
worst case. **Realistic running peak** (the scripts' actual cleanup: the raw BAM,
filtered BAM, per-cell BAMs, and per-chromosome split are all kept -- there's no need
to delete anything to stay in budget -- only the redundant pre-sort CB-filtered copy is
dropped) is lower still, on the same order as the pessimistic figure minus that one
duplicate, i.e. still comfortably under 2.5 TB. Slice D fits with substantial headroom
either way; no aggressive intermediate cleanup is required for space reasons (the
scripts still do the one cheap deletion as hygiene, not because it's needed to fit).

## Must-have: copy-out on completion

`07_copy_out.sbatch` copies the per-cluster somatic VCFs, call-stats, and coverage
files, the SECEDO clustering assignment and reference-relative VCFs, and this run's
logs to `PERSIST_DIR`, then verifies the VCF count matches before declaring success.
`submit_all.sh` chains it with `--dependency=afterany` (not `afterok`) on the mutect
array job, so the copy still runs -- and reports what did or didn't complete -- even if
some (cluster, chromosome) tasks fail, rather than stranding a completed subset in
scratch.

## Report at completion

Once the run finishes, report explicitly: **how many clusters SECEDO found** (stage 05's
`n_clusters` line) and **the somatic SNV count per cluster**, summed across chromosomes
(stage 07's `cluster_summary.csv`). This is the number that tells us whether slice D's
real-data regime lands in the sparse tens-to-hundreds-of-mutations-per-node range
Tree-HDP is built for, or somewhere else -- the actual point of running this slice.
